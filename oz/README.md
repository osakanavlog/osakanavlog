# OZ プロトタイプ

`docs/oz/` の設計図を、実際に動く最小実装にしたものです。
共有空間を歩き、群衆の中で人に会い、花札こいこいで対戦できます。

設計図のうち「同期」「関心管理」「認証と認可の分離」「対戦ルーム」の四つを、
動かして確かめられる形に落としています。

---

## 動かす

```bash
cd oz
npm install
npm start
# → http://localhost:8787
```

二人で遊ぶときは、別のタブか別の端末から同じ URL を開きます。
同じ区画に入り、相手の姿が見えます。

| 操作 | 内容 |
| --- | --- |
| `W` `A` `S` `D` / 方向キー | 移動 |
| `E` | 半径 10 m 以内の相手に対戦を申し込む |
| `C` | サーバ側の対戦相手と花札こいこい |
| `Enter` | 発言（頭上に吹き出しが出る） |
| ホイール | 拡大縮小（引くと遠景の群衆が見える） |

環境変数：`PORT`（既定 8787）、`OZ_BOTS`（群衆ボットの数、既定 900）。

```bash
npm test   # サーバを起動して WebSocket で通しの試験を走らせる
```

## 何が動いているか

### 1. サーバ権威と端末側予測（設計図 04 章 §3）

端末が送るのは**方向だけ**です。座標は一切送りません。
サーバは 20 Hz の固定 tick で入力を処理し、確定した位置を返します。

端末は同じ歩幅で自分の動きを先に描き（予測）、サーバの確定値が届いたら
未確定の入力だけを再適用して差を吸収します（再調整）。
HUD の「予測補正」が、その 1 tick あたりのずれです。
回線の模擬遅延を 400 ms にしても、自分の操作感は変わりません。

不正な入力はサーバが落とします。1 tick に処理する入力は最大 4 件、
入力ベクトルは長さ 1 に正規化され、超過分は棄却されて HUD の「棄却」に出ます。
速度を 30 倍にした入力を大量に送っても、瞬間移動はできません。

### 2. 関心管理の三段階（設計図 04 章 §1）

| 段階 | 距離 | 頻度 | 送る内容 |
| --- | --- | --- | --- |
| 近傍 | 0〜30 m | 20 Hz | 個体として。位置・向き・名前・発言 |
| 中景 | 30〜200 m | 2.5 Hz | 代表点のみ。位置と色 |
| 遠景 | 200 m 〜 | 0.5 Hz | 個体を送らない。50 m 四方の密度格子だけ |

遠景の群衆は、密度格子から端末側で手続き的に生成しています。
一人ひとりの座標は届いていません。画面右下の全体図が、その密度そのものです。

### 3. 認証と認可の分離（設計図 03 章）

- 端末には `oz.device` という鍵の代わりの識別子が保存され、外へは出ません。
- 入場時に **10 分で失効するセッション資格情報**と交換します。HUD に残り時間が出ます。
- 初期の保証レベルは **AL1**（入場・移動・発言）。
- 賭けを伴う操作には **AL2** を要求します。確認なしの申し込みはサーバが拒否します。
  ブラウザの確認ダイアログが、生体認証や PIN の再確認にあたります。
- 保証レベルはセッション全体には昇格しません。操作のたびに要求されます。

### 4. 対戦ルーム（設計図 04 章 §5）

花札こいこいを、サーバを権威として実装しています。
手札はサーバが視点ごとに絞って配るため、相手の手札は**枚数しか届きません**。
同じ乱数の種からは同じ展開になります。

賭けの対象はコインだけです。**アカウントと権限は、勝敗によって移転しません。**
原作では対戦の賭け金がアカウントそのものでしたが、それは「勝てば他人になれる」ことを
意味し、認証の前提が崩れます。ここは設計図で意図的に変えた部分です。

実装した役：

| 役 | 文 | 役 | 文 |
| --- | --- | --- | --- |
| 五光 | 10 | 猪鹿蝶 | 5 |
| 四光 | 8 | 赤短 | 5 |
| 雨四光 | 7 | 青短 | 5 |
| 三光 | 5 | 花見で一杯 / 月見で一杯 | 5 |
| タネ 5 枚〜 | 1 + 追加 1 枚ごと | タン 5 枚〜 | 1 + 追加 1 枚ごと |
| カス 10 枚〜 | 1 + 追加 1 枚ごと | | |

倍率は、合計 7 文以上で 2 倍、相手のこいこい宣言後にあがると 2 倍（こいこい返し）。
払いは「文 × 賭け金（2 コイン）」で、相手の残高を超えて動くことはありません。

簡略化した点：親決めは席順で固定、手四・くっつきは未実装、一局のみで場をまたぎません。
山札から引いた札が同月 2 枚と合う場合は、価値の高い方を自動で取ります
（手札から出した札のときだけ、取る側を選べます）。

## 実測値

MacBook 相当の 1 コアで、群衆ボット 900 体、クライアント 1 台の場合。

| 指標 | 値 | 備考 |
| --- | --- | --- |
| tick | 20 Hz | サーバ側の計算は 10 秒ぶんで 41 ms |
| 下り（広場の中、近傍 55 体） | 約 440 kbps | 近傍の個体同期が支配的 |
| 下り（広場の外、近傍 3 体） | 約 95 kbps | 同じ区画でも位置で 4 倍以上違う |
| 1 tick のスナップショット | 95〜4,000 B | 近傍の人数しだい |
| 往復（模擬遅延 50 ms のとき） | 130〜150 ms | 模擬遅延 × 2 + tick の待ち |
| 予測補正 | 0.0 cm | 予測が当たっている限りずれない |

設計図 01 章の見積もりは「標準品質で約 100 kbps」でした。
広場の外では一致しますが、群衆の中では 4 倍以上になります。差の理由は二つです。

1. 設計図は**二進の量子化表現**（1 アバター 24 B）を前提にしていますが、
   この実装は読みやすさを優先して JSON を使っています（1 アバター 約 40 B）。
2. 設計図は関心管理で実効 60 体程度まで絞る前提ですが、
   ここでは近傍 30 m の全員（最大 120 体）を 20 Hz で送っています。

HUD を見ながら広場の中と外を歩くと、関心管理が効いている量がそのまま数字で出ます。

## 設計図にあって、ここに無いもの

プロトタイプの範囲外です。実装していないことを明示しておきます。

| 設計図 | 実装状況 |
| --- | --- |
| 端末のセキュア領域に置く取り出せない鍵（FIDO2 / パスキー） | 端末識別子による模擬。本物の鍵ではない |
| 分散型識別子、用途別の資格情報、ゼロ知識証明による選択的開示 | 未実装 |
| リアルワールド・ゲートウェイ、リスク階層、帯域外承認 | 未実装（AL2 の要求だけを実装） |
| 監査ストア、ハッシュ連鎖、外部アンカリング | 未実装 |
| 区画の適応的分割・統合、区画をまたぐ引き継ぎ | 未実装（単一区画のみ） |
| 経済台帳の二相確定 | 単純な残高更新のみ |
| 音声、翻訳パイプライン | 未実装（テキスト発言のみ） |
| クラウド描画、アバター規格（VRM / glTF） | 未実装（2 次元の簡易表示） |
| QUIC / WebTransport、二進プロトコル | WebSocket + JSON |
| TLS、認証の暗号学的検証 | なし。localhost で動かす前提 |

このまま公開ネットワークに置くことは想定していません。

## ファイル構成

```
oz/
  server/
    index.js     静的配信、WebSocket、tick ループ、対戦ルームの仲介
    world.js     区画シミュレーション、関心管理、群衆ボット、入力検証
    koikoi.js    花札こいこいの権威実装と役判定
    cards.js     花札 48 枚の定義
  public/
    index.html   画面の骨組み
    style.css    見た目
    client.js    予測と再調整、補間、三段階の描画、HUD
    duel.js      対戦ルームの UI と札の描画
  test/
    smoke.js     サーバを起動して WebSocket で通しに確認する試験
```
