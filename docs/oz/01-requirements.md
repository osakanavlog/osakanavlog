# 01. 要件定義

原作『サマーウォーズ』の描写を観察可能な事実として列挙し、
それを実装可能な要件に翻訳します。翻訳の過程で「そのままでは危険な性質」は
意図的に設計を変えます。変更した箇所は理由を明記します。

---

## 1. 原作描写からの要件抽出

| # | 原作の描写 | 導かれる要件 | 本設計での扱い |
| --- | --- | --- | --- |
| R-01 | 世界中の人が同じ空間にいる | 超大規模同時接続 | 採用。ただし「同じ空間に見える」方式で実現 |
| R-02 | ひとつのアカウントで全サービスを利用 | 統合アイデンティティ | 採用。ただし認証と認可を分離 |
| R-03 | 行政手続・買い物・決済が完結する | 現実サービス連携 | 採用。ゲートウェイ経由に限定 |
| R-04 | インフラ制御まで OZ 上にある | 重要インフラ連携 | **不採用**。読み取りと要求のみに限定（理由は §4） |
| R-05 | 携帯・ゲーム機など非力な端末から入れる | 広範な端末対応 | 採用。クラウド描画を併設 |
| R-06 | 言語が違っても会話できる | 自動翻訳 | 採用 |
| R-07 | アバターが所有者の身体のように動く | 低遅延の入力反映 | 採用 |
| R-08 | アバター同士が対戦し、勝者がアカウントを得る | 競技機能と所有権移転 | 採用。ただし ID 本体は賭けの対象にしない |
| R-09 | 管理者権限が存在する | 特権操作と監査 | 採用。特権は常に複数人承認 |
| R-10 | 単一の攻撃者が世界を麻痺させた | — | **これを起こさないことが第一の非機能要件** |

## 2. 機能要件

### 2.1 アイデンティティ
- 利用者はひとつの OZ ID で全機能に入場できる。
- OZ ID は署名鍵の集合であり、事業者のデータベース上の行ではない。
- 各サービスへの接続は、ID 本体ではなく **用途別の派生資格情報** を用いる。
- 端末紛失時、利用者は回復手続によって新しい端末に ID を再構成できる。
- 利用者は自分の ID に紐づく接続先の一覧を閲覧し、個別に切断できる。

### 2.2 仮想空間
- 利用者はアバターとして空間に入場し、移動・発話・身振り・物の受け渡しができる。
- 近傍のアバターは個体として正確に描画され、遠景の群衆は統計的に再現される。
- 空間は複数の区画から構成され、利用者は境界を意識せず移動できる。
- 空間内のイベント（催事、競技、集会）は数万人規模まで収容できる。
- 利用者は所持品と通貨を持ち、他者と授受できる。

### 2.3 コミュニケーション
- テキスト、音声、身振りの三系統をすべて翻訳の対象とする。
- 話者の言語と聞き手の言語が異なる場合、聞き手側で自動的に変換される。
- 翻訳前の原文・原音声は常に参照できる（誤訳の検証のため）。

### 2.4 現実サービス連携
- 行政手続、決済、予約、配送追跡などを空間内の窓口から利用できる。
- すべての連携は「要求の提出」であり、結果は連携先が確定させる。
- 利用者は自分が出した要求の履歴を時系列で参照できる。

### 2.5 運用機能
- 区画単位、機能単位、連携先単位での遮断ができる。
- 特権操作はすべて記録され、事後に第三者が検証できる。
- 事故時、利用者の資産と ID は仮想空間の状態から独立して保全される。

## 3. 非機能要件

| 分類 | 要件 | 目標値 |
| --- | --- | --- |
| 遅延 | 自入力の自端末反映 | 50 ms 以下 |
| 遅延 | 近傍他者への反映（同一地域） | 100 ms 以下（p95） |
| 遅延 | 対戦ルーム内の入力反映 | 30 ms 以下（ロールバック込み） |
| 遅延 | 音声翻訳（発話終端から再生開始） | 1.2 s 以下（p50）、2.5 s 以下（p95） |
| 規模 | ピーク同時接続 | 1 億セッション |
| 規模 | 区画あたり権威管理アバター | 500 体 |
| 規模 | 見かけの同居人数 | 100 万人 |
| 可用性 | 入場・ID 機能 | 99.99% |
| 可用性 | 個別区画 | 99.9%（失っても入場は継続） |
| 耐障害 | 単一地域全損時 | 90 秒以内に別地域で入場再開 |
| 一貫性 | 経済台帳 | 強一貫（二重支払いを許容しない） |
| 一貫性 | 空間状態 | 結果整合（近傍のみ権威一貫） |
| 安全 | 重要インフラへの自動実行 | ゼロ（人手承認を必須とする） |
| 監査 | 特権操作の記録欠損 | ゼロ |

## 4. R-04 を採用しない理由

原作では上下水道、交通信号、救急搬送の割り当てまでが OZ 上で完結しており、
アカウント乗っ取りがそのまま物理世界の停止に直結しました。
これは設計上の必然であって、攻撃者が特別に有能だったからではありません。

本設計では、仮想空間から現実インフラへの経路を次の三点で切ります。

1. **書き込み権限を持たせない。** 仮想空間側が生成できるのは要求メッセージのみ。
2. **承認を別系統に置く。** 承認系は OZ ID では認証されず、物理トークンと専用網を用いる。
3. **速度を落とす。** 重要度の高い要求には最低滞留時間を設ける。
   即時実行できないことは、この領域では欠点ではなく安全装置です。

この三点により、「OZ が全部乗っ取られた」状態でも、
現実側が受け取るのは承認されない要求の山であり、物理挙動は変わりません。
詳細は [06 章](06-real-world-gateway.md) を参照。

## 5. 規模算定

### 5.1 帯域

近傍 200 体の状態更新を 20 Hz で送る場合：

| 項目 | 値 |
| --- | --- |
| 1 アバターの差分状態 | 24 B（位置 12 B・回転 6 B・状態フラグ 6 B、量子化後） |
| 近傍数 | 200 体 |
| 更新頻度 | 20 Hz（近傍外は 2〜5 Hz に間引き） |
| 実効の平均更新対象 | 約 60 体/tick（関心管理で絞った後） |
| 下り本体 | 約 29 kbps |
| 群衆・環境・イベント | 約 40 kbps |
| 音声（Opus, 1 人分ミックス済） | 32 kbps |
| **合計（標準品質）** | **約 100 kbps** |

1 億同時接続時の総下り帯域は約 10 Tbps。
これは単一データセンタでは不可能な量であり、
世界 40 拠点程度のエッジ配置と、群衆データのマルチキャスト的配信が前提になります。

クラウド描画を使う端末は 1 セッションあたり 8〜15 Mbps を要するため、
全体の 5% までに制限し、超過分は簡易描画モードへ誘導します。

### 5.2 計算

| 項目 | 値 |
| --- | --- |
| 区画サーバ 1 プロセスの権威アバター | 500 体 |
| 1 億同時接続に必要な区画プロセス | 20 万 |
| 1 物理ノードあたりのプロセス | 8〜16 |
| 必要ノード数（区画のみ） | 1.2 万〜2.5 万台 |
| 群衆合成・翻訳・描画を含む総計 | 概ね 4 万〜6 万台 |

### 5.3 保存

| データ | 1 アカウントあたり | 10 億アカウント |
| --- | --- | --- |
| ID・資格情報 | 8 KB | 8 TB |
| 所持品・経済履歴 | 200 KB | 200 TB |
| ソーシャルグラフ | 40 KB | 40 TB |
| 監査ログ（1 年） | 2 MB | 2 PB |
| アセット（共有・重複排除後） | — | 5〜20 PB |

監査ログが最大の保存対象になります。これは意図した結果です。
記録を削って費用を下げる判断は、事故時に最も高くつきます。
